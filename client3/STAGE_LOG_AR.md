# سجل تنفيذ المراحل — client3

## المرحلة 0 — تثبيت خط الأساس

- فحوص CI الأولية نجحت في حل التبعيات واختبارات Flutter وتحليل Dart.
- فشل بناء APK في المحاولة الأولى بسبب مسار Java ثابت من جهاز Windows داخل android/gradle.properties؛ أزيل المسار الثابت حتى يستخدم Gradle بيئة Java لدى runner.
- أصبح بناء APK اختيارياً عند تشغيل سير العمل يدوياً، حتى لا يتكرر انتظار البناء الطويل مع كل تغيير صغير.

## المرحلة 1أ — أساس الاتصال بخادم Flask

- أضيفت `lib/core/network/api_config.dart`: عنوان API مركزي قابل للتبديل، وتطبيع عنوان الخادم، وحل روابط الوسائط من جذر المضيف.
- أضيفت `lib/core/network/flask_api_client.dart`: عميل Dio مركزي لطلبات GET وPOST وPATCH وDELETE، مع مهلات وBearer token اختياري وتوحيد أخطاء Flask.
- أضيفت اختبارات لعنوان API وروابط الوسائط وبادئة `/api/v1` وAuthorization ورفض العناوين الخارجية واستجابة `error/detail`.
- لم توصل الطبقة بعد بمستودعات المنتجات أو المصادقة ولم تُزل تهيئة Supabase؛ ذلك متعمد حتى تُراجع الاستجابات وتُنشأ المحولات في مرحلة منفصلة.

**النتيجة:** Client3 Flutter CI نجح في `flutter pub get` و`flutter test` و`flutter analyze`. بناء APK اليدوي لم يكن مطلوباً.

## المرحلة 2 — تدقيق عقد Flask (تم التدقيق المصدرّي)

- راجعت تسجيل Blueprints الفعلي وأسماء المسارات في ملفات الوحدات، لا مستندات المسارات وحدها.
- وثّقت الفرق بين `catalog/categories` المسطحة وشجرة الفئات التي يجب بناؤها داخل Flutter، وحددت `catalog/products/feed` كمسار بطاقات العميل الذي يعيد الصور وحقول التسعير والمخزون عند توفرها.
- وثّقت معاملات feed وفرز الأسعار، والتغليف المختلف للاستجابات (`items` / `item` / كائن مباشر)، ومسارات العميل الآمنة `commerce/me/cart` و`commerce/me/orders`.
- أضيف `lib/core/network/flask_endpoints.dart` لتجميع المسارات المؤكدة في مكان واحد، واختبارات تمنع الرجوع إلى المسارات القديمة غير المؤكدة.
- حدثت `API_MAPPING_AR.md` بتفاصيل حقول الاستجابات والفجوات ومراجع المصدر.
- لم يتم تغيير أي ملف Flask أو قاعدة بيانات أو migration.

**حدود هذه النتيجة:** التدقيق مؤكد من المصدر. لم أتمكن من تأكيد استجابات الإنتاج الحية من اتصال الأدوات الحالي، لذلك لا أصف اختبار OTP أو feed أو الأسعار بأنه اجتاز اختباراً حياً. يبقى اختبار الدخان من صفحة الويب بعد نشرها أو من بيئة متصلة بالخادم.

## تشغيل الويب على GitHub Pages

- حُوّل `.github/workflows/client-pages.yml` ليبني `client3/` بدلاً من `client2/`، ويشغّل اختباراته وتحليله قبل البناء والنشر.
- يُبنى الويب مع `API_BASE_URL=https://takhfidsh.alattab.site/api/v1` وتُضبط قاعدة المسار لكل من `zydan25.github.io/altakhfidalsh/` والنطاق المخصص.
- بناء APK لا يدخل في هذا المسار؛ بناء الويب هو المطلوب لمعاينة تعديلات الواجهة.
- إعداد Pages الفعلي والنشر النهائي يُعدان مؤكدين فقط بعد نجاح GitHub Actions.

## ما لم يُنجز بعد

- مستودعات TStore ما زالت تستخدم Supabase؛ لا تُعتبر المنتجات/الدخول/السلة متصلة بـFlask لمجرد وجود عميل API ومسارات موثقة.
- المرحلة التالية مستقلة: ربط الكتالوج في التطبيق نفسه (محولات Category/Product/Media، ثم Repository وواجهة الرئيسية/التصنيفات/البحث) مع حالات التحميل والفراغ والخطأ. توقفت عند نهاية المرحلة 2 قبل بدء هذا الربط.
