# خطة تحويل TStore إلى التطبيق البديل للتخفيض الصح

## الهدف والحدود
- تجهيز تطبيق عميل ثالث داخل `client3/` بواجهة TStore، مستقلاً عن `client/` و`client2/`.
- ربط التطبيق بخادم Flask وقاعدة البيانات الحالية عبر REST API؛ لا ننشئ Backend أو قاعدة بيانات موازية.
- لا تعديل على التطبيقين الحاليين أو لوحة الإدارة أو قاعدة البيانات أو إعدادات النشر خلال العمل على client3.
- نُبقي تصميم TStore قدر الإمكان ونغيّر طبقات الإعدادات والاتصال والمستودعات ومحوّلات JSON، لا الشاشات لمجرد اختلاف شكل البيانات.

## خط الأساس
- المصدر: https://github.com/mahmoodhamdi/TStore
- نسخة المصدر التي فُحصت: commit `129431026dfb564fd8cd9186aed5b3109533937b` على `main`.
- المصدر يعلن Flutter 3.38.4 وDart 3.10.3 وBLoC/Cubit وGetIt وClean Architecture، ويستخدم Supabase للمصادقة والبيانات والتخزين وبعض الوظائف الفورية.
- README المصدر يعلن MIT لكنه يحيل إلى ملف `LICENSE` غير موجود في شجرة المصدر التي فُحصت. يبقى التحقق من الترخيص الفعلي مطلوباً قبل النشر العام أو التوزيع التجاري؛ لا نفترض وجود نص ترخيص غير موجود.
- لا ترفع ملف `.env` أو مفاتيح Supabase أو بيانات التوقيع أو أسرار الدفع إلى GitHub أو إلى APK.

## القواعد الهندسية
1. عنوان API واحد مركزي وقابل للتبديل عبر `--dart-define=API_BASE_URL=...`.
2. عميل HTTP واحد لمعالجة المهلات وJSON والأخطاء ورفع الملفات؛ لا يُرسل Bearer token إلا لخادم التخفيض الصح.
3. كل نطاق بيانات له Repository/Adapter. الشاشات لا تتصل مباشرةً بـSupabase أو HTTP.
4. السعر النهائي والمخزون وحالة الطلب هي مسؤولية الخادم؛ لا يصبح الحساب المحلي مصدراً للحقيقة.
5. لا بيانات وهمية ولا اعتبار ميزة مكتملة لمجرد وجود الشاشة أو نجاح البناء.
6. أي ميزة لا يقابلها endpoint مؤكد توثّق كفجوة قبل تنفيذ أو تعطيل واجهتها.
7. توثّق نتائج كل مرحلة ويظل العمل محصوراً في `client3/` ما لم يعتمد تغيير مستقل للخادم.

## المراحل

### 0 — تثبيت خط الأساس
- تسجيل commit المصدر، وملفات الإعداد والمنصات والأصول.
- مراجعة `pubspec.yaml` و`.gitignore` ومتطلبات `.env` وعدم تضمين ملفات أسرار.
- تشغيل `flutter pub get` و`flutter analyze` والاختبارات وبناء Android تجريبي قبل تغيير طبقة البيانات.
- عزل أخطاء المصدر الأصلية وتوثيقها.

**القبول:** نتائج أوامر البناء والتحليل والاختبارات مسجلة، ولا توجد أسرار في الملفات أو تاريخ Git.

### 1 — الإعداد وطبقة النقل
- إضافة إعدادات بيئية واحدة لأصل API والمهلات وأصل الوسائط.
- بناء عميل مركزي باستخدام Dio/HTTP يعالج JSON وأخطاء Flask `error/detail` وانقطاع الاتصال ورفع الملفات.
- نقل حفظ الرموز إلى تخزين ملائم وآمن، وعدم طباعتها في السجلات.
- إزالة اعتماد Supabase تدريجياً بعد نقل كل خدمة؛ لا نحذف الحزم مبكراً قبل التأكد من عدم استخدامها.
- اختبار عميل API منفرداً دون واجهة.

**القبول:** عميل مركزي يعمل باختبارات ويستخدم عنوان Flask، ولا يرسل رموزاً لنطاقات صور خارجية.

### 2 — تدقيق عقد Flask
- اعتماد `docs/API_CONTRACT_AR.md` ومسارات Flask الفعلية في `app/` ثم اختبار endpoints في بيئة اختبار.
- توجد اختلافات بين العقد و`client2/API_MAPPING_AR.md` في مسارات السلة والطلبات وبعض مسارات التصنيفات. يجب حسمها من تسجيل المسارات والاختبار الفعلي؛ لا نفترض صحة `/commerce/me/...` أو أي مسار آخر من الاسم فقط.
- توثيق طريقة HTTP والتوثيق والمعاملات وشكل JSON والترقيم والأخطاء والحقول التي تتطلبها كل شاشة.
- اختبار روابط الصور والخيارات والخصومات والعملات والمخزون.

**القبول:** الخريطة مبنية على endpoints مؤكدة واستجابات فعلية وليست افتراضات.

### 3 — الصفحة الرئيسية والكتالوج
- إنشاء محولات Category وProduct وMedia وVariant وPrice.
- ربط الفئات المتداخلة وقوائم المنتجات والبحث والفرز والفلاتر.
- ربط الصفحات والبنرات والأقسام بعد التحقق من المسارات والاستجابة.
- الاحتفاظ بتصميم TStore قدر الإمكان وإظهار حالات التحميل والفراغ والخطأ.
- عرض صور وأسعار حقيقية فقط، وعدم استخدام سعر أو مخزون افتراضي عند فشل API.

**القبول:** الصفحة الرئيسية والتصنيفات والبحث وتفاصيل المنتج تعرض بيانات Flask الفعلية.

### 4 — الملابس والمتغيرات والتسعير
- ربط اللون/المقاس بمعرّف Variant الفعلي وبالمخزون المرتبط به.
- منع إضافة المتغير غير المتاح وإظهار صور اللون إذا أعادها الخادم.
- تطبيق سياق العملة والمدينة/المنطقة من الخدمة، وعرض السعر النهائي الذي يحسبه الخادم فقط.
- إظهار السعر السابق والخصم والنسبة عند توفرها في الاستجابة.

**القبول:** لا تختلط أسعار أو مخزونات المتغيرات، وتتطابق الأسعار مع رد الخادم.

### 5 — حساب العميل والمصادقة
- استبدال Supabase Auth بتدفق OTP: طلب الرمز، التحقق، `/customer/me`، التجديد والخروج.
- ربط الملف الشخصي والعناوين والمفضلة حيث توجد endpoints مؤكدة.
- اختبار انتهاء الجلسة وتجديدها ومنع الوصول إلى بيانات مستخدم آخر.
- عدم ترك تسجيل الدخول الاجتماعي أو غيره مفعلاً إذا لم يكن له تكامل فعلي.

**القبول:** الدخول والخروج واستعادة الجلسة والعناوين والمفضلة تعمل بحساب اختبار.

### 6 — السلة والشراء والطلبات
- ربط السلة بمعرّف العميل ومعرّف المتغير والكمية والخيارات المختارة.
- جلب طرق الشحن والدفع من Flask وإنشاء الطلب باستخدام المسار الفعلي المؤكد.
- ربط تفاصيل الطلب والحالة والشحن والتتبع وإثبات الدفع عندما يدعمها الخادم.
- اختبار إعادة المحاولة ومنع تكرار الطلب والتحقق من السعر والمخزون على الخادم.
- لا يُفعّل دفع حقيقي قبل اعتماد تكامله واختباره.

**القبول:** ينشأ طلب تجريبي يمكن مراجعته من API ولوحة الإدارة مع تطابق السعر والخيارات والحالة.

### 7 — المراجعات والدعم والإشعارات والترويج
- نقل مراجعات المنتجات إلى API الخادم مع التحقق من الصلاحية.
- ربط المحادثات والمرفقات بواجهات الدعم؛ لا نصفها بأنها فورية ما لم تتوفر آلية realtime مثبتة.
- ربط الإشعارات ورمز الجهاز بعد اختبار الإذن والوجهة عند الضغط.
- ربط الكوبونات والحملات والمحفظة والهدايا فقط حيث يدعمها الخادم.
- توثيق أي ميزة لا يقابلها API وعدم الرجوع إلى Supabase بصمت.

**القبول:** الوظائف المرحّلة تستمد بياناتها من Flask وتوجد قائمة فجوات صريحة.

### 8 — العربية وRTL وتجربة الملابس
- إضافة تعريب كامل للشاشات والنماذج ورسائل الخطأ والتحميل، وليس للصفحة الرئيسية فقط.
- جعل العربية وRTL افتراضياً وفحص ترتيب الأيقونات والحقول والتنقل والأرقام والعملات.
- مواءمة واجهات المنتج للمقاسات والألوان والشارات والخصومات والشحن مع الحفاظ على هوية TStore البصرية.
- إزالة النصوص التجريبية والبيانات الثابتة والمنتجات الوهمية.

**القبول:** لا توجد نصوص إنجليزية غير مقصودة أو تجاوزات أفقية في الشاشات الأساسية على الهواتف الصغيرة.

### 9 — اختبارات التسليم
- تشغيل `flutter pub get` و`dart format --set-exit-if-changed` و`flutter analyze` و`flutter test`.
- بناء APK تجريبي واختباره على جهاز Android.
- اختبار التدفق الكامل: التصفح، البحث، اختيار لون/مقاس، السلة، العنوان، إنشاء طلب تجريبي ومراجعته إدارياً.
- اختبار 401/403/404/500 والمهلات والاستجابات الفارغة وفشل رفع الملفات.
- التأكد من عدم تغيير `client/` أو `client2/` أو قاعدة البيانات والنشر.

**القبول النهائي:** نجاح البناء والتحليل والاختبارات وتوثيق الميزات المكتملة والفجوات المتبقية.

## تعريف الإنجاز
لا تعتبر الميزة مكتملة إلا عندما تتصل بواجهة Flask الفعلية، وتعالج التحميل والفراغ والفشل، وتحترم صلاحيات العميل، وتجتاز اختباراً أساسياً. نجاح بناء APK وحده لا يكفي.
