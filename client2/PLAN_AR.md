# خطة نقل تطبيق client2 إلى خادم التخفيض الصح دون تغيير التصميم

## الهدف

تشغيل تطبيق Flutter المستخرج من الأرشيف مع خادم Flask الحالي:

- عنوان API: `https://takhfidsh.alattab.site/api/v1`
- إبقاء تصميم المصدر كما هو: الشاشات، ترتيب العناصر، الألوان، الخطوط، الأيقونات، الحركة، والتنقل المرئي.
- تغيير مصدر البيانات وآلية المصادقة وحفظ الجلسة في طبقة البيانات فقط، مع محوّلات للبيانات عندما تختلف بنية JSON بين المصدر والخادم.
- إبقاء التطبيق الأصلي `client/` كما هو تمامًا. كل العمل الخاص بالتطبيق الثاني محصور في `client2/`، مع توثيق أي حاجة لتعديل الخادم قبل تنفيذها.

## قواعد تمنع الانحراف عن المطلوب

1. لا إعادة تصميم، ولا إعادة بناء للشاشات، ولا تغيير للـ widgets أو الثيم بهدف التجميل.
2. لا تعديل على `client/` أو تغيير طريقة تشغيله أو نشره.
3. لا استبدال نموذج UI ببيانات خام من Flask؛ تُحوَّل استجابات الخادم إلى النماذج التي تتوقعها واجهات المصدر.
4. لا إرسال مفاتيح WooCommerce أو أسرار الدفع إلى التطبيق. المصادقة الجديدة تستخدم جلسة الخادم ورمز Bearer.
5. لا حذف أي ميزة قديمة بصمت. إذا لم توجد لها واجهة مكافئة في Flask، توثَّق كفجوة ويُحدَّد بديل قبل تعطيلها.
6. كل مرحلة لها فحص قبول قبل بدء المرحلة التي تليها، مع الرجوع إلى هذه الخطة عند ظهور أي حاجة لتغيير التصميم.

## نتائج الفحص الأولي

المصدر مشروع Flutter قديم نسبيًا، ويستخدم حاليًا:

- `lib/src/resources/wc_api.dart`: استدعاءات WooCommerce REST تحت `/wp-json/wc/v2/`، وبناء روابط المصادقة باستخدام مفاتيح WooCommerce.
- `lib/src/resources/api_provider.dart`: استدعاءات WordPress AJAX مثل `/wp-admin/admin-ajax.php?action=mstore_flutter-keys` و`mstore_flutter-products`، مع إدارة Cookies خاصة بـ WordPress.
- `lib/src/config.dart`: إعداد عنوان WordPress ومفاتيح API وإعدادات أخرى.
- نماذج وBLoC وشاشات تعتمد على بنية استجابات WooCommerce/WordPress؛ لذلك لا يكفي تغيير عنوان URL فقط.
- `pubspec.yaml` الأصلي يحدد Dart قديمًا (`>=2.7.0 <3.0.0`) وحزم Flutter قديمة. يلزم فحص توافق البناء قبل تحديث الحزم، ويجب ألا يُستخدم هذا كسبب لتغيير شكل الواجهات.

خادم Flask يوثّق عقد API في `docs/API_CONTRACT_AR.md`. توجد طبقة اتصال أولية مستقلة في `lib/src/flask_api_client.dart` وملف مواءمة في `API_MAPPING_AR.md`؛ يُعاد استخدام ما ينجح منهما بدل بناء اتصال موازٍ غير ضروري.

## مراحل التنفيذ

### المرحلة 0 — تثبيت خط أساس آمن

- تثبيت نقطة مرجعية من `main` قبل التعديلات.
- تسجيل الشاشات وتدفقات الاستخدام الأساسية من المصدر: الرئيسية، الفئات، البحث، تفاصيل المنتج، السلة، تسجيل الدخول، الحساب والطلبات.
- حفظ أسماء النماذج والحقول التي تستخدمها الشاشات، وتحديد الاختبارات الممكنة.
- عدم إدخال أي تغييرات في واجهة المستخدم.

**قبول المرحلة:** نعرف ملفات طبقة البيانات وملفات الواجهة التي يجب إبقاؤها دون تعديل، ولدينا نقطة رجوع واضحة.

### المرحلة 1 — وضع المشروع في جذر client2 وتجهيز بنية البناء

- جعل `client2/` هو جذر Flutter الفعلي: `pubspec.yaml` و`lib/` و`android/` و`ios/` و`web/` وملفات الاختبار في المستوى الصحيح.
- الاحتفاظ بملفات التوثيق العربية الحالية ودمج ملفات المصدر دون حذف طبقة الاتصال الأولية.
- عدم نقل `local.properties` الخاص بجهاز المطور؛ هذا ملف محلي يُنشأ على بيئة البناء ولا ينبغي مشاركة مساره المحلي.
- الحفاظ على الأصول والخطوط والصور وأيقونات التطبيق وملفات إعداد المنصات كما وردت في المصدر في هذه المرحلة.
- فحص قيود Dart وإصدارات الإضافات، وتحديث أقل قدر لازم من إعدادات البناء فقط إذا تطلبت بيئة Flutter الحالية ذلك، دون إعادة كتابة الواجهات.

**قبول المرحلة:** جذر المشروع صحيح، والملفات الأصلية موجودة، وأي تعديل في البناء مسجل، ولا تتغير ملفات `client/`.

### المرحلة 2 — تدقيق عقد الخادم قبل ربط الشاشات

- مقارنة كل طلب مصدر فعلي مع مسار Flask وطريقة HTTP ومعلمات الطلب وشكل الاستجابة.
- التأكد من أن المسارات موثقة وموجودة فعليًا؛ لا نفترض تطابق WooCommerce مع Flask.
- تسجيل الفجوات في `API_MAPPING_AR.md`: حقول الصور، الأسعار والعملة، المخزون، المتغيرات (اللون/المقاس)، الصفحات الديناميكية، الترقيم، الأخطاء، والمرفقات.
- تجربة المسارات العامة أولًا، ثم المسارات المحمية بعد تجهيز حساب اختبار ورمز دخول صالح.
- إذا احتاجت الشاشة حقلًا لا يرجعه الخادم، نحدد هل الحقل غير مدعوم أم أن المحوّل يستطيع اشتقاقه بأمان؛ لا نضع قيمًا وهمية.

**مسارات مرجعية مبدئية** (يُراجع شكل JSON لكل منها قبل استخدامها):
- الصفحة الرئيسية والبنرات ومحتوى المتجر: `GET /storefront/home`، `GET /storefront/banners`، `GET /storefront/pages/{code}`، `GET /storefront/looks`.
- الفئات والمنتجات: `GET /catalog/categories`، `GET /catalog/products`، `GET /catalog/products/feed`، `GET /catalog/products/{id}`، `GET /search/products?q=...`.
- حساب العميل: `POST /customer/auth/request-otp`، `POST /customer/auth/verify-otp`، `POST /customer/auth/refresh`، `POST /customer/auth/logout`، `GET/PATCH /customer/me`.
- العناوين والمفضلة: `/customer/me/addresses` و`/customer/me/wishlist`.
- السلة والطلبات: `GET/POST /commerce/me/cart`، `/commerce/me/cart/items`، `/commerce/me/orders`، `/commerce/me/orders/{id}/detail`، `GET /commerce/shipping-methods`، `GET /commerce/payment-methods`.
- دعم العملاء: `/support/conversations`، `/support/conversations/{id}/messages`، ومرفقات المحادثة.
- مراجعات المنتج: `GET /after_sales/reviews/product/{product_id}` و`POST /after_sales/reviews`.
- الإشعارات ورمز الجهاز والسياسات: مسارات وحدة `notifications` وتسجيل رمز الجهاز تحت `/customer/me/push-token` و`/system/policies`.

### المرحلة 3 — إنشاء طبقة نقل ومواءمة واحدة

- اعتماد عميل HTTP مركزي لعنوان Flask، والمهلات، وJSON، ومعالجة الأخطاء، ورفع الملفات.
- قراءة رمز Bearer من مخزن جلسة مناسب لكل منصة، وإرساله فقط إلى أصل API الخاص بنا، وعدم إرساله إلى روابط صور أو مواقع خارجية.
- إنشاء محوّلات منفصلة حسب الحاجة مثل `ProductAdapter` و`CategoryAdapter` و`CartAdapter` و`CustomerAdapter`.
- إبقاء نماذج العرض كما هي قدر الإمكان؛ إذا اختلف نموذج البيانات، يكون التغيير داخل طبقة المستودعات/المحوّلات لا داخل الـ widgets.
- توحيد التعامل مع حالات التحميل والنتيجة الفارغة وأخطاء الشبكة دون تغيير مظهرها الحالي.

**قبول المرحلة:** يمكن اختبار طبقة البيانات منفردة، ولا توجد أسرار أو مفاتيح WooCommerce في طلبات العميل الجديدة.

### المرحلة 4 — الرئيسية والكتالوج والبحث وتفاصيل المنتج

ترتيب الربط المقترح:

1. الرئيسية والصفحات الديناميكية والبنرات.
2. الفئات وعلاقاتها وترتيبها.
3. قوائم المنتجات والصفحات التالية والتصفية والبحث.
4. تفاصيل المنتج والصور والسعر والعملة.
5. خيارات المنتج ومتغيراته والمخزون والمفضلة/المشاهدة حيث تدعمها واجهة الخادم.

تُحوَّل استجابات Flask إلى حقول نماذج المصدر، ويُراعى أن الصور قد تصل كرابط مطلق أو كرابط يبدأ بـ `/media/`. لا يعاد ترتيب عناصر الشاشة لتلائم JSON.

**قبول المرحلة:** البيانات الحقيقية تظهر في الشاشات الأصلية مع بقاء التخطيط والألوان والأيقونات كما كانت، وتعمل حالات عدم وجود نتائج والأخطاء.

### المرحلة 5 — الدخول والحساب والعناوين والمفضلة

- نقل المصادقة من جلسات WordPress/Cookies إلى OTP ورمز Bearer الخاص بخادمنا.
- ربط بيانات الحساب والعناوين والمفضلة، وتجديد/إنهاء الجلسة وفق عقد الخادم.
- حفظ الرمز بطريقة ملائمة للمنصة، وعدم تضمينه في ملفات المصدر أو السجلات.
- مراجعة تسجيل الدخول الاجتماعي وFirebase بشكل منفصل: لا يُبقَى تدفق قديم يوحي بنجاح الدخول إذا لم يكن له تكامل مقابل فعلي.

**قبول المرحلة:** تسجيل الدخول والخروج واستعادة الجلسة تعمل بحساب اختبار، والوصول إلى بيانات عميل آخر مرفوض من الخادم.

### المرحلة 6 — السلة وإتمام الشراء والطلبات والدفع

- ربط إضافة/تعديل/حذف عناصر السلة ومعرّفات متغيرات اللون والمقاس والكميات.
- جلب طرق الشحن والدفع من Flask، وإرسال الطلب بالشكل الذي يتوقعه الخادم.
- ربط تفاصيل الطلب وحالاته وإثبات الدفع عند دعم المسارات الحالية لذلك.
- عدم افتراض أن إضافات Stripe أو Paystack أو صفحات WebView القديمة قابلة للاستخدام مع خادمنا؛ تُستخدم بوابة الدفع التي يحددها الخادم فقط.
- اختبار تحديث المخزون وإجماليات الأسعار ومنع تكرار الطلب عند إعادة المحاولة.

**قبول المرحلة:** يمكن إنشاء طلب تجريبي ومراجعة تفاصيله وحالته من API، دون عملية دفع حقيقية قبل إعداد واعتماد التكامل.

### المرحلة 7 — المحادثات والإشعارات والتقييمات

- ربط محادثات العميل ورسائلها ومرفقات الصور/الملفات بـ API الدعم.
- تحديد آلية التحديث الفوري المتاحة في الخادم؛ إن لم تكن مناسبة، يُعتمد تحديث دوري مضبوط بدل ادعاء أن المحادثة مباشرة.
- ربط قراءة الإشعارات وتسجيل رمز الجهاز، والتحقق من فتح الوجهة الصحيحة عند الضغط على الإشعار.
- ربط التقييمات ومرفقاتها وفق الصلاحيات وعقد الخادم.
- مراجعة ميزات Firebase Firestore/Storage/Messaging القديمة؛ لا تُحذف التهيئة قبل التأكد من أن البديل المطلوب يعمل.

**قبول المرحلة:** الرسائل والإشعارات والتقييمات تُقرأ وتُرسل من خادمنا، وتعمل صلاحيات العميل والمرفقات، مع توثيق أي ميزة لا يوجد لها مقابل.

### المرحلة 8 — إيقاف الاعتماد على WordPress بأمان

- البحث عن جميع استدعاءات WooCommerce وWordPress AJAX/Cookies وعن مفاتيح WooCommerce داخل المشروع.
- التأكد من عدم بقاء شاشة أساسية تستخدم مصدر البيانات القديم.
- إزالة أو تعطيل الاعتماد القديم من طبقة الخدمات فقط بعد نجاح كل التدفقات البديلة؛ لا تُحذف ملفات أو حزم قد تستعملها واجهات أخرى قبل فحصها.
- وضع إعدادات البيئة والمفاتيح الحساسة خارج المصدر. مراجعة ملفات Firebase وخرائط المنصات وإعدادات الدفع كلٌّ على حدة.

**قبول المرحلة:** لا توجد طلبات تشغيلية إلى WordPress/WooCommerce في المسارات التي تم ترحيلها، ولا توجد مفاتيح خاصة بالخادم داخل تطبيق العميل.

### المرحلة 9 — الاختبار والتسليم

- تشغيل `flutter pub get` ثم `flutter analyze` والاختبارات، ومعالجة مشاكل التوافق دون تغيير مظهر التطبيق.
- بناء Android debug APK وتجربة تشغيله على جهاز فعلي أو محاكي.
- بناء الويب إذا ظلت كل الإضافات المطلوبة متوافقة مع Flutter Web.
- اختبار الرئيسية والبحث والتفاصيل والدخول والسلة والطلب والمحادثات والإشعارات على حساب اختبار.
- مقارنة لقطات قبل/بعد للشاشات الرئيسية للتأكد من عدم تغيّر التصميم.
- تحديث هذا الملف و`API_MAPPING_AR.md` بنتائج النجاح والفجوات المتبقية.

**قبول التسليم:** توثيق أوامر البناء ونتائجها، وقائمة ميزات تم اختبارها، وقائمة واضحة بما لا يدعمه الخادم بعد.

## فجوات لا يجوز إخفاؤها

المصدر يتضمن ميزات مرتبطة بمنظومة WordPress إضافية مثل حسابات/واجهات البائعين، وبعض محتوى المدونة والدفع والمحادثات المبنية على Firebase. لا يعني وجود شاشة في المصدر أن خادم Flask يقدم API مقابلًا لها. ستُسجَّل كل فجوة، ويُختار لكل منها تكامل مدعوم أو تُترك غير مفعلة لحين حسم البديل؛ لا تُزوّر استجابات ولا نغيّر تصميم الشاشة لتعويض نقص البيانات.

## ترتيب العمل بعد النقل

1. استكمال تدقيق البناء والتوافق دون أي تعديلات مرئية.
2. بناء خريطة طلبات فعلية من المصدر إلى المسارات المثبتة في Flask.
3. تنفيذ طبقة الاتصال والمحوّلات واختبارها مستقلة.
4. نقل الميزات تباعًا بدءًا من الرئيسية والكتالوج، ثم الدخول، ثم السلة والطلب، ثم بقية الخدمات.
5. فحص البناء ومقارنة التصميم بعد كل مجموعة تغييرات.

> هذه الخطة لا تدّعي أن التطبيق أصبح متصلًا بالخادم بعد النقل؛ الاتصال الفعلي مرحلة مستقلة ولا يبدأ إلا بعد تثبيت بنية المشروع ومطابقة عقد البيانات.


## سجل التنفيذ الفعلي — المرحلة الأولى

**الحالة الحالية: فحوص التوافق الآلية قيد التشغيل؛ لا تُعد المرحلة مقبولة حتى تنتهي جميع خطوات CI بنجاح.**

تم تنفيذ التحضيرات التالية داخل `client2/` فقط:

- الإبقاء مؤقتًا على نطاق Dart الأصلي `>=2.7.0 <3.0.0` بدل فرض ترقية SDK قد تكسر ملفات المصدر القديمة.
- تعديل عميل Flask الأولي ليستخدم صياغة متوافقة مع لغة Dart القديمة المعلنة في المشروع؛ لم تُعدّل أي شاشة أو ملف تصميم.
- تصحيح استيراد اختبار العميل كي يطابق اسم الحزمة الحالي `app`.
- التصريح عن حزم `crypto` و`path` و`path_provider` التي يستوردها المصدر مباشرةً.
- إضافة سير عمل مستقل `.github/workflows/client2-ci.yml` يجرب Flutter 2.2.3 وJava 8، ثم ينفذ `flutter pub get` و`flutter test` و`flutter analyze` وبناء APK تجريبيًا.
- عدم تغيير إعدادات تطبيق `client/` أو خادم Flask أو إعدادات الإنتاج.

### معيار قبول المرحلة الأولى

لا ننتقل إلى ربط الشاشات قبل تسجيل نتيجة تشغيل واضحة لكل من حل التبعيات، والاختبارات، والتحليل، وبناء Android. إذا فشل أي منها، نصلح سبب الفشل المحدد بأقل تعديل ممكن، ثم نعيد تشغيل CI. لا نرفع إصدار Flutter أو الحزم الرئيسية عشوائيًا؛ أي ترقية كبيرة تحتاج خطة توافق منفصلة لأنها قد تمس الشفرة القديمة.
